# 前端职级评审、定级与校准基线

- 文档版本：V1.0（试行）
- 生效日期：2026 年 9 月 28 日
- 制度负责人：前端负责人

> 本基线面向直属负责人、评审委员会和校准参与者使用。
> 职级责任和相邻职级边界以 [前端岗位职级标准与发展指南](frontend-leveling-standards.md) 为准；本基线用于核验事实、形成结论和完成校准。

## 一、评审适用范围

- 适用职级：P2、P3-1、P3-2、P3-3、P4-1、P4-2、P4-3、P5。
- 适用岗位：业务研发、工程平台、技术专家/架构师和前端管理岗位。
- 评审前记录目标职级、工作方向、实际授权和责任范围；P4 及以上确认技术或管理主通道。评审记录须注明所采用标准的版本或归档副本。
- P4 及以上需要形成清晰的主通道，但主通道优势不能抵消共同底线中的明显缺失。

## 二、评审输入与判断顺序

评审不先计算总分，也不能先看个人最擅长的能力再反推职级，应按以下顺序判断：

1. **确认责任范围**：确认实际承担的任务、功能、模块、领域、系统责任，或团队、多个业务单元、组织级管理责任，并核对授权与结果范围。
2. **确认主通道**：区分技术、管理责任，再结合业务研发、工程平台等工作方向选择结果证据；管理通道按对应子级的团队、跨单元或组织级责任评价。
3. **核验复杂度与自主性**：确认成员是否承担了目标拆解、方案取舍、依赖协调、风险控制和长期结果责任。
4. **核验六个能力维度**：按公开标准的分职级要求核验业务理解与交付、技术基础与实现、架构与工程效能、质量稳定性与安全、复杂问题与决策、协作影响与人才发展，记录事实与证据。
5. **核验持续结果**：确认结果是否经过后续运行、复用、交接或多个独立周期验证。
6. **区分个人贡献**：说明本人责任、关键判断和关键动作，不能只引用团队结果或个人口述。
7. **形成定级结论并校准**：使用统一结论口径，由跨团队人员复核事实和证据。

## 三、复杂度、有效案例与持续性

### 复杂度判断

复杂度不是代码量、技术名词或项目人数，而是需要本人承担判断和风险的约束组合。评审至少应说明以下因素中的实际难点：目标是否模糊、依赖和协作是否跨边界、变更影响范围、失败影响和恢复成本、方案是否可逆、长期维护和迁移成本。

- **低复杂度**：目标、方案和验收标准较清晰，影响局部，依赖少且容易回滚。
- **中复杂度**：实施路径、依赖或验收存在实质性不确定性，需要主动拆解、方案取舍和风险控制，通常涉及跨模块或多角色协作；须说明具体约束如何影响决策和结果。
- **高复杂度**：涉及跨项目/跨团队、核心链路、迁移兼容、遗留约束或较高失败成本，需要定义系统边界并对长期结果负责。
- **组织级复杂度**：除高复杂度约束外，还涉及多个业务线或组织单元的资源优先级、标准治理、长期机制或决策方式变化。

达到目标职级不要求每个案例同时包含所有复杂度因素，但必须明确哪几项约束构成案例难点，以及成员对这些约束承担了什么责任。

### 有效案例判断

有效案例是一个能够说明“背景—责任—判断—行动—结果—持续性”的完整闭环，并满足以下条件：

- 本人的责任边界、关键判断和关键动作可以被他人核验，不能只有团队结果或个人口述。
- 结果与本人承担的责任存在合理归因，并有交付记录、方案/RFC、监控数据、采用记录、复盘或协作反馈等证据支撑。
- 每个独立案例须有可单独验收的目标、本人关键判断、行动及结果。多个案例还须体现不同目标或实质不同的决策约束；同一方案下的编码、联调、上线步骤，以及同一结果的不同指标，不重复计数。
- 项目交付、稳定性治理、复杂问题预防、领域建设和知识转移都可以成为案例，前提是有可验证结果，不能只记录动作数量。

### 持续性判断

持续性指结果不是上线或完成当日的短期现象，而是在后续交付、运行、采用或交接中仍然成立。满足以下任一条件，可作为持续性证据：

- 结果在多个独立交付周期中重复成立，或长期项目经过多个可验证里程碑仍保持有效。
- 方案经过后续运行和维护，缺陷、稳定性、效率或成本改善趋势没有立即反弹。
- 能力被其他项目、业务线、团队成员或共同维护者实际接手和复用，成员减少日常介入后仍能正常运行。

不以统一月数作为持续性门槛。评审必须记录观察周期、结果是否复用、交接是否完成，以及仍存在的依赖。

### 证据组合与责任覆盖

P3-2 及以上可采用以下任一组合。混合使用项目案例和治理记录时，须共同证明至少两次在不同目标或实质不同约束下的关键判断及其结果，并完成后续持续性验证；不得重复计算同一次判断或同一结果。评审者须记录采用方式及其覆盖的核心责任。

| 证据形式 | 接受条件 | 不足以认定的情况 |
| --- | --- | --- |
| 独立案例 | 至少两个有效案例；本人在不同目标或决策约束下持续承担目标职级责任，并有后续运行结果 | 两个普通任务、两个仅执行他人方案的项目，或把团队结果全部归于本人 |
| 长期项目 | 至少两个可独立验收的里程碑；每个里程碑分别记录目标、关键取舍和运行或采用结果，并说明与其他里程碑的责任区别 | 将设计、开发、测试当作三个案例；反复引用同一次上线结果 |
| 长期治理或运营职责 | 提供连续履责记录，覆盖至少两个与业务、发布或治理节奏对应的观察窗口；包含至少两次有实际取舍的判断及后续结果，并有协作者确认本人责任 | 仅报“没有事故”、仅列例会或巡检次数，或将同一期间的数据切片凑数 |

观察窗口须记录起止时间及选择依据，覆盖一次措施执行后的运行验证，并在后续窗口验证效果保持或调整结果。单个项目仍在早期且未形成独立里程碑或持续治理记录时，应记录尚缺的证据与复核时间。

证据是否充分按以下要求判断：

1. 对照公开标准的本级核心责任、所选通道和六个能力维度，逐项关联事实与材料。一个案例可以覆盖多项要求；案例数量达标不能抵消核心责任缺失。具体任务和行为示例允许以等价证据证明，须记录对应条款，并说明责任范围、复杂度、自主程度、影响范围与持续结果为何相当；不因成员未经历某类项目、重构或故障而直接判为未达到。
2. 核心责任须有达到目标范围的事实。局部贡献可证明对应能力，但不能借项目规模推定本人承担了整体责任。
3. 持续治理可以证明稳定达成目标，无须每个周期都提高指标；须说明业务量、系统变更、人员负荷等条件，以及本人采取的措施、实际结果和未解决风险。历史数据不足时，使用验收、运行、演练和协作记录交叉印证，不补造基线或收益。
4. 知识转移以他人实际独立承接为证据，记录承接前后的责任、支持程度和运行结果；文档或培训数量不能代替承接效果。
5. 仅有职责描述、潜力判断或未来计划时，记录缺口并补证。未分配对应机会的，按第六节安排责任机会。

## 四、证据核验要求

每条核心证据至少回答以下问题：

1. **背景**：业务目标、约束、规模和当时基线是什么？
2. **责任**：本人承担什么责任，哪些不是本人负责？
3. **判断**：比较过哪些方案，为什么这样选择，接受了什么代价？
4. **行动**：本人完成了哪些关键动作，如何协调他人和控制风险？
5. **结果**：业务、质量、效率、成本或人才结果如何，口径和周期是什么？
6. **持续性**：结果是否持续，是否被复用，减少本人介入后能否正常运行？

以下内容不能单独证明职级：

- 工作年限、学历、原公司头衔或管理人数。
- 会使用某个框架、构建工具、AI 产品或底层技术名词；AI 使用次数、生成代码量或工具使用率。
- 代码行数、文档数量、会议次数、加班时长或救火次数。
- 一次高光项目、一次重大故障处置或缺少上下文的百分比指标。
- 只有团队结果，无法说明本人责任、判断和关键贡献。

| 能力维度 | 主要材料与认定依据 | AI 相关材料（适用时） |
| --- | --- | --- |
| 业务理解与交付 | 需求、目标拆解、里程碑和验收记录；确认本人承担的目标、范围与风险处理结果 | 需求边界修订及业务确认记录，能区分生成建议与已确认规则 |
| 技术基础与实现 | 方案、代码评审、接口与运行记录；确认关键取舍及实现质量。管理岗位提供评审意见和风险处理结果 | 生成内容的评审修改、测试与运行结果，能解释采纳、修改或放弃的原因 |
| 架构与工程效能 | 架构、流程、采用与维护记录；按本级责任范围确认复用效果、成本和维护责任 | P2、P3-1 提供实践及验证记录；P3-2、P3-3 提供模块或领域改进记录；P4、P5 提供相应范围的采用、维护及效果记录 |
| 质量、稳定性与安全 | 测试、发布、监控、权限检查、故障或演练记录；确认风险发现、控制及后续验证 | 生成测试的实际执行、遗漏补充、错误修正，以及按公司要求进行的数据处理与权限控制记录 |
| 复杂问题与决策 | 备选方案、日志、实验、资源取舍和结果记录；确认本人判断、接受的代价和后续调整 | 对生成假设的实证检验和方案取舍记录 |
| 协作、影响与人才发展 | 协作反馈、授权和独立承接记录；确认他人能承担的责任及本人贡献 | P2、P3-1 提供实践反馈和评审修改；P3-2、P3-3 提供协作应用结果；P4、P5 提供跨项目、跨单元或组织级采用与维护结果 |

材料可来自已有研发和管理记录，按案例引用即可。成员提供的材料须遵守公司数据访问与脱敏要求。

## 五、定级结论与最低证据规则

定级结论只使用三种口径：

- **达到目标职级**：责任范围、复杂度、自主程度和影响范围均达到目标职级，并有持续结果证据。
- **未达到目标职级**：存在明确事实证明核心责任或共同底线未达到要求。
- **证据不足**：责任机会不足、案例归因不清或观察结果不足，尚不能确认目标职级。须记录具体缺口和下一次复核条件，不据此认定能力不足。

统一判断规则如下：

1. 高一级默认稳定满足低一级核心要求，不能只凭某个突出技术点跨级。
2. 同一职级允许岗位通道不同，但责任复杂度、自主性和影响范围应保持同等价值。
3. P3-2 及以上按第三节的证据组合认定，须证明多次关键判断及持续履责，逐项覆盖目标职级核心责任。
4. P2 提供在指导下完成任务及验证的记录；P3-1 至少提供一个完整功能交付案例及上线后的运行记录，两者均不要求团队级方法推广。
5. P4 技术通道须证明相应范围的跨项目技术影响；管理通道须证明对应子级的团队、跨单元或组织级管理结果。两类通道均须证明知识转移和替代运行；P5 须证明组织级持续结果。
6. 团队结果必须区分本人贡献，个人结果也要说明团队支持和业务上下文。
7. 定级争议应回到事实和证据，由跨团队人员使用同一标准校准，不能由单一直属负责人按印象决定。

存在已核实的核心责任不达标事实时，应形成“未达到目标职级”的结论并列明依据；仅缺材料或观察时间时，使用“证据不足”。材料齐备且全部核心责任与适用共同底线得到证明，方可形成“达到目标职级”。评审者意见不同是待处理状态，不能直接当作能力或证据不足的结论。

## 六、“证据不足”与责任机会

对“证据不足”的结论，评审必须继续追问责任机会是否被合理提供，并记录：

- 过去周期是否安排过与目标职级相匹配的责任机会；如果没有，原因是业务约束、资源分配、负责人判断还是个人明确选择。
- 如果机会已经提供，成员实际承担了哪些责任，为什么仍未形成有效证据；不能用“没有机会”替代事实判断。
- 如果确实缺少机会，直属负责人需要给出下一周期的成长任务、责任范围、支持方式、验收标准和观察周期，并在后续校准中复核。

连续多个周期没有提供合理责任机会时，负责人需要解释机会分配和培养安排；不能一边不给机会，一边仅以“证据不足”作为长期不调整职级的理由。

## 七、岗位通道与共同底线核验

P4 及以上逐项核验[公开标准第六节](frontend-leveling-standards.md#六岗位通道边界)的五项共同底线，在每项后记录事实、证据来源、结论和未解决问题。不得以主通道成绩抵消共同底线中已核实的明显缺失。

- 技术通道：按对应子级核验系统、领域或组织级技术责任，接受评审、共同维护、知识交接等人才发展证据。
- 管理通道：核验实际授权、目标与资源决策、质量结果、成员或负责人独立履责情况，不以个人代码产量或是否亲自建设平台判定。
- 管理 P4-1 须证明稳定团队持续运行；P4-2 须证明多个独立目标单元通过负责人机制协同运行；P4-3 须证明组织授权范围内跨团队治理或项目组合的持续结果。只扩大人数、增加会议或获得头衔均不构成责任升级。
- P5 技术通道核验整体技术战略、跨领域投资与长期业务收益；管理通道核验前端组织整体目标、资源配置、组织健康与负责人梯队。按主通道分别核验六个能力维度，不将人员管理权限作为技术通道达标条件。
- 缺少带教对象时，可用评审、交接、轮值或共同维护证明他人独立承接；如未形成目标职级所需的结果，仍须记录事实或机会缺口。

## 八、校准与偏差防范

校准时应主动防范以下偏差：

- 用工作年限代替能力证据。
- 用口才、可见度、加班和救火频率代替持续贡献。
- 对业务研发和平台研发使用完全相同的结果指标。
- 只奖励新建系统，不认可维护、治理、迁移和降低复杂度的价值。
- 把团队共同结果全部归给负责人，或忽略低职级成员的关键贡献。

每次评审至少由直属负责人和一名跨团队评审者共同核验关键结论。评审记录必须包含目标职级、主通道、责任范围、核心案例、证据来源、结论、主要缺口和下一周期动作。

### 分歧处理

分歧由直属负责人统一收集、核对和转述，协调评审方核实，并向成员反馈处理结果。处理安排结合本次评审确定；公司已有申诉流程或审批权限的，按公司制度执行。

- **收集与转交**：保留成员和评审者的原始意见、争议条款及相关证据，转述内容由意见提出者核对。直属负责人将分歧提交有权处理的负责人或评审组织，明确处理责任人和反馈安排。
- **核实与判断**：评审方区分事实、标准适用和证据充分性分歧，核对材料并允许补充说明。仍有争议时，由有权处理的负责人或评审组织安排未参与原结论、无利益冲突且具备相应通道经验的人员复核，并在授权范围内确认结论。无法核实的材料不用于认定达标或不达标；不得临时增加职级门槛。
- **反馈与闭合**：直属负责人向成员反馈结论、条款依据和意见采纳情况，并留存记录。需要补证或后续观察的，按第五、六节明确缺口、支持安排与复核时间，由直属负责人跟进；发现实质新证据或标准适用错误时重新复核。分歧以有依据的结论及反馈记录闭合，不要求成员必须认同结论。

涉及直属负责人本人或对其公正性有异议时，成员可直接向更上一级负责人或公司指定评审组织反馈。负责人是被评人、争议原结论的直接作出者或存在利益冲突时，复核人员指定、复核组织和结论确认一并交由更上一级或公司指定评审组织负责。涉及第三方隐私的材料仅向有权限的评审者开放，并向成员提供必要事实摘要。

### 评审记录

| 记录项 | 必填内容 |
| --- | --- |
| 评审范围 | 标准版本或归档副本、目标职级、工作方向、主通道、实际授权、观察起止时间 |
| 责任与证据 | 标准条款、本人事实、材料链接或可查记录、核实人、采用的证据组合及等价认定依据（适用时） |
| 逐项判断 | 核心责任、六个能力维度及适用共同底线的达成情况；缺失事实与缺失材料分别记录 |
| 综合结论 | 三种结论之一、主要理由、已验证结果、缺口与限制 |
| 分歧与复核 | 原始意见与核对后的转述、处理责任人、反馈安排、复核与确认人、处理结论及采纳依据；无分歧时注明 |
| 反馈与后续 | 成员反馈日期、事实更正、责任机会、支持安排、验收标准和复核日期 |

## 九、不可补偿红线

以下问题不能依靠其他维度高分直接抵消，但必须基于事实调查和公司制度处理，不能仅凭评价者主观印象：

- 伪造经历、数据、结果或隐瞒重大事实。
- 明知存在重大质量、安全或合规风险仍绕过流程上线，造成严重影响。
- 对事故、延期或风险故意隐瞒、推诿责任，拒绝参与止损和复盘。
- 使用 AI 或外部工具处理敏感数据、引入代码时违反安全与许可要求，且未履行审查责任。
- 通过侮辱、威胁、打压异议、信息垄断或职级压制破坏团队协作。

## 十、制度边界

本基线规定能力评审、分歧处理及后续验证要求。面试、绩效、晋升名额、答辩形式和薪酬映射按公司相应制度执行。能力达到目标职级与职级、薪酬调整的审批分别记录，不以名额或预算原因改写能力结论。
