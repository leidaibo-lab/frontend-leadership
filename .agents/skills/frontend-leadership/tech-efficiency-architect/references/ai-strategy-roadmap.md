# 前端团队 AI 实践路线图

本路线图用于安排试点、流程接入和后续能力建设，属于规划参考。具体周期、预算和效果目标需要在明确场景与基线后确定。

整体推进方向以[AI Coding 跃迁总览](ai-coding-evolution.md)为入口：表达与项目接入、加法与减法最终收束到工程化建设。本文的试点阶段用于安排任务和资源，与实践架构图中的 V1.0/V2.0 方案版本分别记录。

研发效率的判断应覆盖需求确认、实现、评审、测试和返工。工具覆盖率或生成速度可以作为过程信息，但不能单独证明交付改善。

## 内部分享中提出的试点方向

已开展的[“AI 驱动组织运行模式升级讨论”分享](ai-organization-operating-model-sharing.md)提出三个候选场景：需求评审前 AI 预审、前端提测前自查、Bug 复盘规则沉淀。建议先从中选择两到三个，明确参与人和观察方式后试运行；目前尚未记录试点启动或效果。

这三个场景是本次讨论的具体建议。下文各阶段提供可选的推进方式，不要求先完成全部编码辅助任务，才开始需求预审或复盘实践。

## 起步：选择一个能核对结果的场景

从当前重复工作或协作阻塞中选择问题，例如表单实现、接口联调准备、需求边界检查或测试用例补充。记录任务复杂度、原有处理方式、耗时和缺陷，再明确 AI 介入范围及人工检查点。

试点开始前需要确定：

- 场景负责人和参与角色。
- 允许使用的数据、模型与工具。
- 输入材料、验收条件和失败处理方式。
- 基线、样本选择、观察周期和成本记录。
- 推进、调整或停止试点的条件。

## 阶段一：验证实现与检查任务

可以先选择以下任务，按实际问题取舍：

| 任务 | 实施方式 | 验证重点 |
| --- | --- | --- |
| 组件或表单草案 | 提供现有组件接口、业务规则和异常状态 | 代码能否运行，复用是否正确，人工修改与返工投入多少 |
| 测试用例补充 | 根据需求、实现和历史缺陷生成候选用例 | 用例是否验证真实行为，能否发现错误，是否遗漏关键边界 |
| 代码审查辅助 | 提供变更、调用上下文和项目规则 | 有效问题、误报、遗漏及人工审查成本 |

试点效果通过实际执行记录确认，不预设固定采纳率、测试覆盖率或错误拦截比例。质量和安全要求继续按项目标准执行。

## 阶段二：处理跨角色交接

在第一阶段经验基础上，与产品、后端和测试共同选择协作问题。

设计稿转代码需要同时提供交互状态、组件规范与业务约束；生成静态页面后还要验证行为和集成。接口或 Mock 草案需要前后端确认契约及版本，再用于并行开发。

这一阶段重点观察等待确认、变更同步和返工。有效做法写入评审清单、任务模板和知识记录，并指定维护人。

## 阶段三：评估业务场景与公共能力

如果业务侧有明确需求，再验证知识问答、数据查询或助手类交互。前端负责展示与交互，鉴权、数据访问、模型密钥和业务操作校验应在受控服务侧处理，不能因接入模型而绕过既有权限。

流式展示、取消与重试、错误反馈等交互能力有重复使用需求时，可以整理为公共组件。是否建设组件库或服务平台，取决于实际采用场景、维护资源与收益。

## 资源与协作安排

| 资源 | 需要确认的事项 |
| --- | --- |
| 模型与工具预算 | 使用场景、供应商策略、额度、费用归属与退出安排 |
| 数据与权限 | 可用资料范围、脱敏、访问控制及日志要求 |
| 实施与维护人员 | 试点、规则维护、质量验证和问题处理的负责人及时间投入 |
| 协作方支持 | 业务确认、接口评审、测试与上线责任 |
| 培养与交接 | 成员能解释生成结果、发现错误，并掌握必要的排障与验证方法 |

工具选型随能力、成本和公司策略调整，不将特定产品或模型名称作为长期路线的前提。

## 阶段复盘

每阶段结束后，记录实际收益、额外审查和维护投入、质量变化及未解决问题。能够稳定复用且投入合理的做法继续推广；结果不足时缩小范围或调整方法。

评估记录可参照[前端 AI 效能验证框架](frontend-ai-efficiency-framework.md)。对外引用数字前，应能说明样本、基线、周期和归因限制。
