# 个人管理时间线与文章事实源

## 目的

本文统一记录用户已经确认的个人管理时间线、团队规模变化、关键阶段和事件证据。后续写管理文章、述职、分享稿或个人成长复盘时，应先读取本文，再读取当前团队快照，避免用当前人数反推管理起点。

事实使用顺序：

1. 用户最新明确补充的事实。
2. 带日期的个人事件记录。
3. 述职报告和项目内既有材料。
4. Agent 基于事实做出的归纳。

发生冲突时，以上层事实为准。Agent 归纳必须标明为“阶段判断”“正在验证”或“尚未证明”，不能改写成用户原话或既成结果。

## 四个关键阶段

### 阶段一：6人景云销团队，主要依靠直接推进和口头对齐

- 第一个项目是景云销，团队经历了艰苦推进阶段。
- 开始接触多团队之间的矛盾，也开始处理产研外部矛盾。
- 团队内部主要靠口头对齐，管理依赖个人跟进和现场协调。

### 阶段二：新项目和中台目标出现，开始减少口头管理

- 第二个项目进展尚未稳定时，又接到建设中台的目标。
- 预判团队还会大规模扩充，开始思考如何减少口头对齐。
- 这一阶段的变化不是突然理解管理，而是提前为业务和人员扩张做准备。

阶段二的精确年月和当时人数尚未单独确认。写作时可以使用业务阶段，不要擅自绑定具体年份或人数。

### 阶段三：中台基础成型，开始下放压力和职责

- 中台基础成型后，团队内外协作仍然混乱。
- 大量协调压力集中在前端负责人个人身上。
- 开始考虑把压力、职责和结果责任一起下放，而不是只分配执行任务。

阶段三的精确年月和当时人数尚未单独确认。当前只能确认它发生在中台基础成型之后。

### 阶段四：28人阶段，从整体可控走向组织能力建设

- 当前整体把控感相对可控，但不能据此判断机制已经成熟。
- 新的关注点包括工程基础建设、质量与稳定性、AI研发治理、架构演进和行业变化压力。
- 管理目标开始同时考虑团队、公司和成员：既保障交付，也让成员共同成长并获得长期收益。

## 带日期的事件证据

### 2025年5月6日：重新划定组长、项目与成员责任

- 用户最初倾向先确定组长，再分配其可辐射的成员范围。
- 上级提出项目必须有明确责任人，再将组长映射到项目。
- 用户认可项目结果优先的判断：组长既把控项目，也管理项目成员。
- 可形成的认知更新：组织分工应先围绕结果责任设计，再确定人员管理范围。

### 2025年5月13日：把团队分享制度交给成员讨论

- 团队公开讨论分享制度。
- 每个人都表达了自己看到的优劣。
- 当前只确认形成了参与和讨论，尚无分享频率、质量或复用结果证据。

### 2025年5月13日：讨论CRM、OMS与仓储模块并行开发的人员规划

- 核心矛盾是多项目人员调度风险。
- 从其他项目调人会影响原项目职责和工作衡量；不调人则供应链人力不足。
- 同时担心老员工缺少能力提升和锻炼机会，团队成长动力不足。
- 该事件说明交付资源配置与成员成长不能分开考虑，最终方案和结果尚未记录。

### 2025年8月4日：提前梳理工程基础建设流程

- 计划在年底建设Web组件库、App组件库和跨端工具库。
- 判断依据是年底业务任务相对减少，适合为下一年高需求阶段做提前量。
- 目标是降低后续复用、一致性、维护和管理压力。

### 2025年12月9日：处理多项目共用App的方案争议

- 多人提出不同接入方案，但彼此无法说服，方案迟迟不能落地。
- 最终由前端负责人拍板，选择更符合团队习惯且更解耦的方案。
- 会议让风险被充分暴露，也形成了讨论氛围。
- 暴露的问题是团队已有表达空间，但仍缺少能快速收敛的技术决策机制。

### 2025年12月9日：推动工程基础建设方案进入实施

- 主动向上级确认方案可行性和流程可落地性。
- 获得确认后完成专项组对齐并召开动员会。
- 当时的判断是20+团队必须统一组件复用，降低维护成本和线上风险。
- 选择年底业务相对较少的时间窗口安排建设。

### 2025年12月10日：主动收集公司多项目后续规划

- 希望通过产品下一年及后续规划判断团队是否有稳定项目承接。
- 用于判断下一年度招聘计划和团队内部人员调整。
- 这说明人员规划开始从当前缺口转向业务前置量，但预测准确性和后续结果尚未记录。

### 2025年12月11日：建立技术决策的商业指标意识

- 技术决策开始主动对应降本、增效、风控、增长4类商业指标。
- 这是判断框架的形成，不代表每项技术决策已经完成量化证明。

### 2026年3月9日：发起技术精进匿名调研

- 通过匿名问卷降低表达压力，观察成员是否能发现问题并提出解决方案。
- 增加抽奖环节，提高参与意愿和团队活力。
- 结果显示少数成员目标具体，多数目标仍偏抽象，极少数成员没有理解问卷意义。
- 当前能证明的是成长目标清晰度不足，不能据此直接判断个人没有成长性。

### 2026年3月9日：校准业务线负责人推动能力

- 发现部分业务线负责人本身也存在事项推动困难。
- 用户在“直接换人”和“保持团队稳定”之间犹豫。
- 当前选择是继续带领并设置1个月考核观察期。
- 这是正在验证的管理动作，不能写成负责人机制已经成熟或人员调整已经完成。

## 28人阶段可以形成的阶段判断

以下内容是根据用户时间线和事件记录形成的归纳，不是用户已经确认的最终结论。写作时应使用“我目前的判断”“还在验证”，不能写成已经证明的管理成果。

### 已有记录支持的判断

1. **口头对齐无法支撑持续扩张**：从6人团队到多项目并行，协作复杂度持续上升，已经推动流程规范、责任划分和知识沉淀。
2. **责任必须围绕项目结果设计**：2025年5月6日的讨论修正了“先定组长再分成员”的思路，转为先明确项目责任人。
3. **职责下放必须连同判断权和结果责任一起下放**：只分任务不能减少负责人个人压力，业务线负责人需要承担推进、风险识别和结果闭环。
4. **工程基础建设需要利用业务低谷提前投入**：2025年8月和12月的记录都表明，等业务高峰再补组件、工具和规范会更加被动。
5. **技术讨论需要明确的收敛机制**：充分讨论能够暴露风险，但无法说服对方时仍需要决策标准、单点责任人和明确时限。

### 当前暴露的新问题

1. **骨干抓不住高优先级事项**：需要区分是目标和上下文没有讲清、骨干缺少深入判断，还是推动节奏和反馈机制不足。
2. **团队边界事项缺少稳定承接人**：工程基础建设等重要但不紧急事项仍容易无人认领，不能直接假设积分制度会解决主动性问题。
3. **授权可能停留在角色名称**：部分业务线负责人自身推动困难，说明任命负责人不等于形成了承担结果的能力。
4. **前端负责人仍可能是决策瓶颈**：技术争议最终仍依赖个人拍板，压力下放和决策机制还没有完全建立。
5. **交付与成员成长存在资源冲突**：跨项目调人既影响原项目，也关系成员锻炼机会，需要明确项目优先级、能力目标和容量保护。
6. **结果证据仍不完整**：当前有大量判断、动作和过程记录，但缺少机制实施前后的交付周期、延期、缺陷、复用率、负责人独立承接比例等对比数据。

## 对外写作口径

- 用户指定这些内容默认可以公开，并会在发布前自行检查。
- 对外文章默认使用业务线、角色和项目名称，不主动展开成员姓名。
- 可以写真实犹豫、冲突和未解决问题，但不把对个体的负面判断写成公开定性。
- 可以写“从2023年3月的6人团队走到当前28人”，不能写“从20人开始理解管理”。
- 可以写“当前整体把控感相对可控”，不能写“28人组织已经稳定自治”。
- 可以写“负责人机制正在验证”，不能写“负责人机制已经证明成功”。
- 可以写“积分制度是待验证设想”，不能写“积分制度已经提升主动性”。
