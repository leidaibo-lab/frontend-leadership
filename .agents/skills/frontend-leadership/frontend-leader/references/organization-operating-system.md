# 30人前端团队可经营组织运行系统

## 定位

本运行系统适用于当前28人、年内目标30+人的前端团队。组织保持4个稳定大团队，通过动态子业务线负责人扩展业务承接能力，并通过工程底座、质量与稳定性、AI研发治理、架构演进4个横向虚拟团队建设组织能力。

核心目标不是增加管理角色，而是让组织具备可分配、可跟进、可验收、可调整和可退出的运行闭环。

> 固定组织归属，单点结果负责，限定横向产能，固定复盘节奏，季度决定继续、调整或退出。

本文定义组织运行规则，不包含个人责任卡或岗位模板。

## 运行闭环

```text
季度确定重点方向和结果
→ 明确负责人、核心成员和最低产能
→ 双周处理结果偏差、风险和决策请求
→ 月度检查纵横矩阵与成员负载
→ 季度验收结果证据
→ 决定继续、调整、转交或退出
```

运行系统只追踪负责人、结果、证据和决策，不把会议次数、分享次数、文档数量等活动本身当作成果。

## 纵向组织约束

### 固定大团队

- 景云销、中台、品牌管理/招投标、供应链4个大团队是稳定组织单元。
- 每位成员只有一个大团队归属，人员管理、业务排期、绩效反馈和本线交付由所属大团队负责人承担。
- 新项目、新业务线和临时专项不直接形成新的平级团队，优先进入业务关联度和能力匹配度最高的现有大团队。
- 每位大团队负责人直接管理的重点子业务线负责人原则上不超过3位；超过时必须复盘管理跨度、业务边界和组织拆分条件。

### 子业务线负责人任命门槛

新业务初期先明确具体事项负责人，不立即形成正式管理层。以下4项满足至少3项，并经过一个季度实际运行验证后，再正式任命子业务线负责人：

1. 业务预计持续两个季度以上。
2. 已形成相对独立的目标、干系人和发布节奏。
3. 已经需要两名以上成员稳定投入，或大团队负责人管理跨度明显超限。
4. 已有能够独立承担需求、方案、交付、风险和复盘结果的人选。

业务不再持续、边界重新合并或负责人无法形成独立结果时，子业务线负责人应降级为事项负责人，不保留空转角色。

### 新增平级大团队门槛

只有以下条件同时成立，才评估拆分新的平级大团队：

- 业务边界长期独立，且有持续稳定的业务目标。
- 人员规模和工作量足以支撑独立团队，而不是短期项目峰值。
- 与原大团队的协作成本已经高于拆分后的治理成本。
- 已有经过验证的大团队负责人梯队，不依赖前端负责人直接接管。

## 横向虚拟团队约束

### 固定方向和人员结构

横向能力保持4个方向：工程底座、质量与稳定性、AI研发治理、架构演进。每个方向采用统一结构：

```text
1位横向负责人
+ 2至3位核心成员
+ 按具体事项邀请的接口人或专业成员
```

- 每个方向只有一位结果负责人，不设置共同负责人或负责人委员会。
- 横向负责人直接向前端负责人汇报能力结果和资源风险。
- 每名成员最多承担一个主要横向方向，避免同一批骨干被多个方向重复占用。
- 横向团队不改变成员的大团队归属，也不直接调整成员的业务优先级。

### 重点建设和运转维护

4个方向可以长期存在，但不同时进行高强度建设：

- 每季度最多2个方向进入重点建设状态，拥有明确核心成员、最低产能和季度结果。
- 其他方向进入运转维护状态，只保留负责人、问题池、必要标准维护和紧急事项响应。
- 没有明确季度结果或无法承诺最低产能的方向，不启动专项建设。

起步阶段，重点方向负责人原则上每周固定投入半天到一天，核心成员按事项承诺投入。实际比例可以根据业务压力调整，但调整后必须同步缩小目标，不能保持目标不变而长期挤占个人额外时间。

## 季度结果契约

每个重点横向方向每季度只承诺：

```text
1个核心目标
不超过2个结果指标
1份可验证结果证据
1个需要前端负责人裁决的关键问题
```

结果指标必须说明能力建设带来的变化，不使用纯活动数量代替：

| 方向 | 优先结果口径 | 不作为单独成果的口径 |
| --- | --- | --- |
| 工程底座 | 接入范围、启动成本、复用率、维护成本变化 | 完成多少组件、写了多少文档 |
| 质量与稳定性 | 重复缺陷、重点问题闭环率、复发验证、线上稳定性变化 | 发现多少问题、开了多少复盘会 |
| AI研发治理 | 流程覆盖、交付周期变化、评审质量、典型场景节省时间 | 工具使用人数、提示词数量、分享次数 |
| 架构演进 | 结构性问题关闭、技术债变化、跨项目一致性、迁移风险下降 | 输出多少方案、召开多少评审 |

## 纵横矩阵使用规则

纵横矩阵的列是4个固定大团队，行是4个横向能力方向。交叉格不是第二条汇报线，只在存在真实建设事项时记录：

```text
接口人或执行负责人
+ 当前建设事项
+ 本季度结果或验收状态
```

- 不要求16个交叉格全部有人或全部有事项，空白表示当前无需投入。
- 同一事项只能有一位执行负责人，其他成员是参与者。
- 月度检查交叉格的目的，是发现重复占用、无人负责、长期无结果和跨团队依赖，不是为了填满矩阵。

## 权限与责任边界

| 事项 | 结果责任 |
| --- | --- |
| 业务优先级、人员安排、项目排期、本线交付 | 大团队负责人 |
| 具体子业务线的需求、方案、交付节奏、风险和复盘 | 子业务线负责人 |
| 横向标准、机制、共性问题和能力结果 | 横向负责人 |
| 跨团队资源冲突、负责人任免、重点方向启停 | 前端负责人 |
| 共性工具和工程能力产品化 | 工程底座负责人及对应执行成员 |
| 质量问题识别、治理计划、验收和复发验证 | 质量与稳定性负责人 |
| 具体整改和业务项目实现 | 所属大团队或明确的执行负责人 |

质量与稳定性负责人可以提出风险、标准和验收结论，但不直接改动业务排期。大团队负责人负责提供整改资源并承担本线质量结果；无法协调时由前端负责人裁决。

## 冲突处理规则

纵向交付和横向建设发生冲突时，按以下顺序处理：

1. 横向负责人明确事项价值、最低投入、截止时间和不投入的风险。
2. 大团队负责人判断本线业务优先级和可提供产能。
3. 双方能够达成一致时，记录调整后的范围和结果承诺。
4. 无法达成一致时，只上浮资源取舍和风险，不把全部执行细节上收。
5. 前端负责人裁决优先级、范围、延期或暂停，并对裁决结果负责。

前端负责人主动跟进的是负责人结果和组织决策，不直接追踪所有成员的行动项。

## 固定管理节奏

### 双周负责人会

- 参与者：前端负责人、4位大团队负责人、当季度重点横向负责人。
- 建议时长：45分钟以内。
- 只讨论本周期结果、当前风险、需要的决策和下周期唯一重点。
- 能在线下闭环的执行细节不进入会议。

### 月度矩阵检查

- 检查重点横向事项是否有单点负责人和结果证据。
- 检查成员是否承担多个主要横向方向。
- 检查16个交叉格中是否存在重复建设、长期无结果或跨团队阻塞。
- 检查大团队负责人的子业务线管理跨度是否接近上限。

### 季度经营评审

- 验收重点横向方向的目标、指标和结果证据。
- 决定下一季度哪些方向重点建设，哪些方向转入运转维护。
- 复盘子业务线负责人是否继续、扩大、降级或退出。
- 对连续无结果的方向和负责人做调整，不让虚拟团队变成永久委员会。

## 项目战队边界

项目战队可以作为重大里程碑或跨业务协作的临时交付机制，但不是主要组织模型。成立时必须明确：

- 项目目标和里程碑。
- 唯一项目负责人。
- 开始时间、结束时间和参与成员。
- 项目负责人只对项目里程碑负责，不拥有成员的长期绩效、组织归属和业务优先级。

项目结束后释放的是项目任务和临时协作关系，成员仍归属原大团队。

## 转交与退出机制

横向虚拟团队不是永久委员会，出现以下情况时必须转交、暂停或退出：

- 共性能力已经产品化，转交工程底座长期维护。
- 质量机制已经稳定进入业务线日常流程，横向团队转为抽查和重点治理。
- AI试点无法形成可验证收益，停止继续扩散。
- 架构决策已经完成，后续实现进入对应业务团队或工程底座。
- 连续两个季度没有形成可验证结果，合并、暂停或更换负责人。

退出不等于能力消失，而是把已经验证的标准、资产和责任转移到稳定组织中，释放虚拟团队的专项产能。

## 运行健康指标

优先使用少量指标判断系统是否有效：

- 大团队负责人直接管理的重点子业务线负责人数量。
- 子业务线负责人独立完成交付闭环的比例。
- 同时重点建设的横向方向数量。
- 成员承担多个主要横向方向的数量。
- 横向季度目标完成率和结果证据完整度。
- 跨团队资源冲突上浮次数及平均关闭周期。
- 已验证能力转交到工程底座或业务线的数量。
- 连续两个季度无结果但仍未退出的虚拟事项数量。

## 反模式

- 为每个新项目新增一个平级团队。
- 子业务线负责人只有头衔，没有业务结果和授权。
- 4个横向方向同时铺开大量任务。
- 16个矩阵交叉格为了完整而强行安排成员。
- 横向负责人直接越过大团队负责人调整成员排期。
- 前端负责人直接追踪所有执行成员，重新成为单点瓶颈。
- 用会议、分享、文档和工具使用人数代替结果证据。
- 虚拟团队长期存在，但没有季度验收和退出机制。
