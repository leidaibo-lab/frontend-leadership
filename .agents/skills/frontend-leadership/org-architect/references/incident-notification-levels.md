# 线上问题通报层级参考

## 来源与采用边界

来源：2026-10-09 提供的历史“通报层级标准”正文，以及同次明确的更新要求。历史正文引用[推广风险点及预案](https://w74x12qb16.feishu.cn/docx/HZ03dS6IrorwekxprGzcw2NinEm)，该链接内容未另行核验。

本文件留存历史口径及当前采用原则；事故执行以[通用线上事故响应流程](../../../../../outputs/incident-response-process.md)为准。历史问题分级 P0-P3 与当前事故分级 P0-P2 不直接等同。

## 当前采用的通报原则

- 发现或升级为 P0/P1 时，必须立即通报 CTO，不能仅停留在当前领域角色负责人知情。
- 对应老板是否需要知情、通知时机和范围，由 CTO 根据影响与风险动态考虑，并明确由谁同步。
- 目标是避免业务方或客户先找到老板或 CTO 时，管理层尚不知情，无法提前安排资源、沟通和风险应对。
- 初报先同步发现时间、现象、已知影响、风险、当前联系人和正在采取的动作；未知信息标记待确认，不等待完整根因和报告。
- 事故负责人负责信息送达和持续更新，可指定记录与沟通负责人执行；接管前由发现人或已知情的当前领域角色负责人先完成紧急通报。
- 记录 CTO 接收确认及老板通报安排。未回复记为待确认，通过电话等直接方式补充联系；通报与止损并行，不改变事故负责人统一协调的职责。
- 后续版本变更应同步相关人员。此次新增要求已明确，团队同步及演练结果尚未记录。

## 历史标准摘要

以下仅用于理解历史背景，不作为当前执行要求。

| 历史等级 | 正文通报范围 | 历史处理要求 |
| --- | --- | --- |
| P0、P1 | 全体产研和老板 | 立即通报、紧急协调，解决后向相关管理层同步报告 |
| P2 | 前后端负责人、产品经理 | 分配处理、确认优先级与修复计划；长期未解决或影响扩大时升级 |
| P3 | 组长、产品经理或助理 | 记录与安排修复，在周会或月会汇总 |

历史文本还包含：等级变化按新等级通报；P0/P1 通过飞书群、微信或电话立即同步；P2/P3 定期同步；P0/P1 解决后 24 小时内提交复盘报告并通报全体；非技术问题由产品或技术负责人判断通报层级。原文中单独的旧 P1 段落已划线废弃。

历史正文与末尾对应表的 P2/P3 接收角色表述存在差异，因此保留来源差异，不据此新增当前角色要求。

## 与现行 SOP 的衔接

| 历史内容 | 当前处理 |
| --- | --- |
| P0/P1 默认通报全体产研和老板 | 采用本次明确的新要求：CTO 必须知情，老板及需扩大的管理通报范围由 CTO 动态判断；相关处理和业务协作人员及时知情 |
| 按 P0-P3 问题等级通报 | 沿用主 SOP 的事故分级；不新增 P3 事故等级 |
| P0/P1 解决后 24 小时内提交复盘并通报全体 | 历史要求留存，未在本次转为现行 SOP 的新增时限或全员通报要求 |
| 紧急问题先同步、等级变化后升级 | 纳入主 SOP，明确通报责任、接收确认和简短格式 |

演练应覆盖“发现人先报、负责人暂时无法响应、初判后升级为 P1、CTO 接收确认、老板通报决定及重大变化再同步”，以记录检验信息是否实际到达。
