# 数据完整性事故处置卡

> 版本：V1.0（草案）
>
> 适用场景：订单、价格、金额、库存、用户信息、状态等核心数据出现错误、丢失或前后不一致
>
> 来源案例：2026 年 9 月终端订单上报数据异常事故
>
> 使用方式：先启动《通用线上事故响应流程》，再按本卡执行具体排查和止损

## 一、触发条件

满足任一条件，立即引用本卡：

- 用户填写值与页面展示、请求参数或落库值不一致；
- 核心数据出现异常值、默认值、空值或错误覆盖；
- 同类异常数量或比例持续增加；
- 无法确认异常是否仍在产生；
- 涉及订单、金额、库存、权益或其他不可轻易恢复的数据。

涉及核心数据时，即使只有个别用户反馈，也按高风险处理，先核查是否存在批量影响。

影响范围未确认前，按 P0 高风险事故组织响应；完成核查后可根据实际影响调整等级。

## 二、角色分工

| 角色 | 处置职责 |
| --- | --- |
| 事故负责人 | 接管事故、统一协调、决定止损和升级、确认关闭 |
| 技术处理负责人 | 定位数据偏差环节，组织修复、回退或替代方案 |
| 后端角色 | 查询请求、接口、数据库和审计数据，执行服务端拦截或数据核查 |
| 当前领域角色负责人 | 提供专业判断、资源和升级支持，保持持续知情 |
| 测试与业务验证角色 | 验证输入、展示、请求、落库和业务结果是否一致 |
| 运维角色 | 提供监控、日志、发布回退和流量控制支持 |
| 产品、运营及其他协助角色 | 确认业务规则、用户影响和补救方案 |
| 记录与沟通负责人 | 维护时间线、决策、影响数据和统一进展同步 |

事故负责人默认由业务线负责人担任；无法及时跟进时，由业务线副手明确接管。

## 三、前 10 分钟：确认并止住新增异常

1. 建立事故沟通渠道，记录发现时间、版本、环境和首条证据。
2. 确认异常是否仍在写入，立即暂停相关发布、热更新和高风险操作。
3. 后端快速查询异常数据趋势，不等待更多用户反馈。
4. 根据风险选择止损措施：
   - 关闭相关入口或提交按钮；
   - 服务端拦截异常值；
   - 回退版本或隔离受影响版本；
   - 限制指定用户、设备或版本继续提交；
   - 切换人工或其他替代流程。
5. 同步当前领域角色负责人、后端、测试、运维、产品和运营等协助角色。

止损动作必须记录执行人、执行时间、影响范围和回退条件。

## 四、30 分钟内：确认影响范围

按以下维度核查，并持续更新结果：

| 核查维度 | 核查内容 |
| --- | --- |
| 时间 | 首条异常、最后异常、修复前后数据变化 |
| 版本 | APP、服务、热更新或配置版本 |
| 用户范围 | 用户、区域、组织、经销商或客户 |
| 环境特征 | 机型、系统版本、网络和操作路径 |
| 数据链路 | 页面展示值、表单状态、请求参数、服务端落库值 |
| 业务对象 | 订单、产品、终端、库存、金额等关联对象 |
| 趋势 | 异常数量、占比、增长速度和修复后的新增情况 |

对于业务上允许出现的异常值，不能仅按字段值判断。应结合用户操作、版本、历史基线和上下游数据区分：

1. 业务合法数据；
2. 系统产生的异常数据；
3. 无法确认来源的数据；
4. 已造成后续业务影响的数据。

## 五、技术排查与恢复

在确认新增异常已停止或已受控后，技术处理负责人组织排查：

1. 定位异常发生在页面展示、状态同步、请求组装、接口处理还是数据库写入环节；
2. 对比正常版本与异常版本、不同设备和关键操作路径；
3. 优先采用回退、服务端拦截或稳定替代方案恢复业务；
4. 修复后验证多条目编辑、高频输入、快速提交、弱网和异常值等场景；
5. 由测试和业务验证角色共同确认关键业务结果；
6. 进入观察期，确认没有新增异常或影响扩大。

## 六、数据恢复与业务补救

数据恢复评估应在新增异常停止、技术方案完成并验证稳定后进行。

1. 核查请求日志、网关日志、缓存、数据库审计、操作记录和业务历史记录；
2. 明确哪些数据可直接恢复、可辅助恢复、无法恢复；
3. 恢复前保留原数据、操作记录和审批信息，禁止无审计覆盖；
4. 对无法恢复的数据，制定人工核验、重新提交、业务修正或其他补救方案；
5. 记录最终影响范围、恢复结果和不可恢复边界。

前端无法恢复用户原始输入值，不等于整个数据链路无法恢复；必须完成后端及业务侧证据核查后再下结论。

## 七、恢复验证与关闭条件

同时满足以下条件，才能结束本卡处置：

- 新增异常已停止，相关监控恢复正常；
- 页面展示、请求参数、服务端处理和落库结果一致；
- 影响范围、异常口径和版本范围已经确认；
- 数据恢复、业务补救或不可恢复边界已经明确；
- 修复版本已完成关键设备和业务场景验证；
- 观察期内没有再次异常；
- 时间线、止损决策、验证结果和遗留事项已经留痕。

本卡结束后，仍需回到通用事故响应流程完成事故关闭和复盘。

## 八、必须沉淀的改进项

- 关键数据写入前后的校验和异常拦截；
- 版本、用户、设备和业务维度的异常数据监控；
- 框架升级、发布和热更新的高风险场景验证；
- 事故负责人、业务线副手和协助角色配置；
- 数据异常应急演练及全量影响核查能力。
