# 数据完整性事故处置卡

> 版本：V1.2（草案）
>
> 适用场景：订单、价格、金额、库存、用户信息、状态等核心数据出现错误、丢失或前后不一致
>
> 来源案例：2026 年 9 月终端订单上报数据异常事故
>
> 使用方式：在[《通用线上事故响应流程》](incident-response-process.md)的对应阶段使用本卡，补充数据完整性场景的检查项。事故分级、接管、响应时限、进展同步和关闭权限统一执行主 SOP。

## 一、发现与上报

发现以下现象时，按主 SOP 启动事故响应并引用本卡：

- 用户填写值与页面展示、请求参数或落库值不一致；
- 核心数据出现异常值、默认值、空值或错误覆盖；
- 同类异常数量或比例持续增加；
- 已发现数据异常，但无法确认是否仍在产生或向下游传播。

发现人保留发现时间、版本、业务对象标识、用户操作、日志和截图等证据，及时通知业务线负责人。涉及订单、金额、库存、权益等核心数据时，个别反馈也需要核查批量影响。

业务线负责人默认担任事故负责人；无法及时跟进时，按主 SOP 明确接管。事故负责人建立统一沟通渠道和事故记录，明确技术处理、业务验证及按需参与的协助人员，同步当前领域角色负责人。

阶段输出：首条异常证据、事故负责人、人员分工和统一事故记录。

## 二、影响判断与止损决策

事故负责人组织初步判断：异常是否持续写入、是否向下游传播、是否涉及核心业务或不可轻易恢复的数据，按主 SOP 确定初始等级和升级范围。影响无法确认时按高风险处理，记录不确定性并立即升级。

根据当前证据进入以下分支：

- 存在持续扩大风险、需要立即控制影响，或无法确认风险：优先执行止损措施。
- 已有证据确认风险可控且无需立即止损：进入受控排查，持续观察影响变化并记录判断依据。

技术处理负责人提出可执行方案，事故负责人决定止损方式并安排执行。按风险选择关闭相关入口、服务端拦截、回退或隔离受影响版本、暂停异常数据向下游流转，或切换人工替代流程。

暂停可能扩大影响的发布、热更新或数据操作；用于止损和恢复的变更由事故负责人组织评估后执行。业务允许的 0 值、空值等不能直接作为统一拦截条件，需结合业务规则确定拦截范围。

阶段输出：初始等级、风险判断、止损决策及执行人、执行时间、影响范围、回退条件和效果证据。止损无效或影响扩大时，立即重新评估并按主 SOP 升级；不等待全量核查或根因定位完成。

## 三、并行开展影响核查与技术排查

事故负责人组织两条工作线并行推进。优先落实止损，但不能因尚未完全止住异常而停止必要的技术排查和影响核查。

### 3.1 业务线负责人或业务线副手牵头影响核查

组织后端、产品、运营及其他相关角色主动查询生产数据，持续更新以下信息：

| 核查维度 | 核查内容 |
| --- | --- |
| 时间 | 首条异常、最后异常、修复前后数据变化 |
| 版本 | APP、服务、热更新或配置版本 |
| 用户范围 | 用户、区域、组织、经销商或客户 |
| 环境特征 | 机型、系统版本、网络和操作路径 |
| 数据链路 | 页面展示值、表单状态、请求参数、服务端落库值 |
| 业务对象 | 订单、产品、终端、库存、金额等关联对象 |
| 趋势 | 异常数量、统计总量、占比、增长速度和止损前后变化 |
| 下游影响 | 是否已影响结算、库存、报表、权益或其他业务结果 |

结合用户操作、版本、历史基线和上下游数据，将数据区分为业务合法、已确认异常、来源待确认三类；另行标注是否造成下游业务影响。

每次统计注明时间窗口、筛选及去重规则、数据来源和待确认范围。疑似数量不能直接作为最终事故影响数量。

### 3.2 技术处理负责人牵头原因排查与方案执行

1. 定位偏差发生在输入、状态同步、请求组装、接口处理、数据库写入还是下游处理环节。
2. 对比正常与异常版本、设备和操作路径，区分已验证结论与待验证假设。
3. 保留请求日志、网关日志、缓存、数据库审计及业务记录等证据，为定位和后续恢复提供依据。
4. 找到可执行方案后，组织修复、回退、降级或替代方案的执行，并记录生效范围和结果。

没有可执行方案时，继续排查或执行临时绕行方案，并返回风险判断，持续确认是否需要补充止损或升级。

阶段输出：影响范围及趋势、原因证据、处置方案和执行记录。进展同步执行主 SOP：P0 默认每 30 分钟同步，P1/P2 按关键节点同步，重大变化立即同步。

## 四、恢复验证与观察

1. 技术处理负责人先确认方案已生效，并验证关键数据链路；使用热更新或版本隔离时，确认实际覆盖范围及未覆盖版本的控制措施。
2. 测试配合验证多条目编辑、高频输入、快速提交、弱网、合法边界值等相关场景；业务验证负责人确认关键业务结果恢复。
3. 对同一业务对象核对输入、展示、请求、服务端处理和落库结果，确认没有新增异常或下游影响扩大。
4. 验证恢复稳定后，按主 SOP 进入不少于 1 小时的观察期，记录观察起止时间、数据范围及监控结果。

验证未通过或观察期内再次异常，返回止损与隔离阶段，由事故负责人组织重新判断和处置。

阶段输出：技术验证、业务恢复确认及观察结果。仅有上线记录不能作为恢复确认。

## 五、残余影响、数据恢复与业务补救

恢复稳定并完成观察后，由业务线负责人或业务线副手牵头评估残余影响。此前已保留的证据和影响核查结果作为评估输入。

- 无残余数据或业务影响：记录核查范围、证据和确认人。
- 存在残余影响：组织相关角色制定恢复或补救方案，执行后核对结果。

恢复或补救时，逐项确认：

1. 根据完整数据链路的证据，明确可直接恢复、可辅助恢复和无法恢复的数据范围。
2. 恢复前保留原数据、操作记录和审批信息，记录执行范围及核对方式。
3. 对无法恢复的数据，落实人工核验、重新提交、业务修正等补救措施。
4. 核对恢复后的数据和下游业务结果，记录最终影响、处理结果和不可恢复边界。

前端无法恢复用户原始输入值，不等于整个数据链路无法恢复，需完成后端及业务侧证据核查后再下结论。

按主 SOP，在修复完成后 1 天内完成影响、数据和业务复核；业务数据产生周期超过 1 天时，以覆盖完整业务周期为准。

阶段输出：最终影响清单、数据恢复或业务补救结果、不可恢复边界，以及未完成事项的负责人、截止时间和后续验证方式。

## 六、事故关闭与复盘

由事故负责人依据主 SOP 第六章统一确认关闭，核对技术与业务恢复、观察结果、残余影响处理和遗留事项记录。所有阶段证据进入同一份事故记录。

复盘按主 SOP 第七章逐项回答，并重点检查本场景的响应情况：

- 是否及时识别数据完整性风险并明确接管，哪些判断有证据、哪些仍待补证；
- 止损是否及时有效，影响核查与技术排查是否并行，延迟或缺失的动作及原因是什么；
- 数据恢复和业务补救是否覆盖最终影响范围，谁承担协调、技术处理、业务判断和恢复验证责任；
- 校验拦截、异常监控、升级回归及协作机制应如何改进，是否需要通过演练验证响应能力。

每项改进必须记录：改进事项、责任人、截止时间、验收标准和验收证据；通过演练、抽查、监控或后续数据验证效果。
