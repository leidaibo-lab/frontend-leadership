## 一、事故结论摘要

本次事故是一起由 APP 前端输入数据同步异常引发的线上数据完整性事故，同时暴露出事故发现、影响评估、紧急止损、跨团队协作和责任接管机制失效的问题。

当前已知判断：

> 终端订单上报页面为优化多产品输入性能，采用了依赖输入事件时序的延迟同步逻辑。APP 升级 RN 0.86 后，该逻辑在部分场景下未能保证用户最后输入值及时同步到提交数据，导致页面展示值、表单状态、请求参数和服务端落库值出现不一致，最终产生异常订单数据。

本次事故不应只归因于“RN 0.86 兼容问题”。更完整的根因是：**关键数据写入链路依赖旧事件时序，升级前缺少专项兼容性验证，提交前缺少最终值校验，生产侧缺少异常数据监控和紧急止损机制，团队又没有及时按高风险事故组织响应。**

## 三、影响范围与数据核查

### 3.1 已知影响

事故期间业务员在 APP 进行终端订单上报，部分订单出现用户填写值与实际提交值不一致的情况。已统计到 5521 条价格为 0 的订单，并按经销商、终端、产品条件筛出 400 条疑似问题订单。

由于业务规则允许用户主动填写 0 元，当前不能直接将全部 5521 条订单认定为事故数据。需要区分：

1. 业务上合法的 0 元订单；
2. 用户实际填写具体价格、但提交或落库为 0 的订单；
3. 其他旧值、默认值或错误值覆盖用户输入的订单；
4. 已造成后续业务影响、需要人工补救的订单。

## 四、事故链路

```text
APP 升级 RN 0.86
→ 输入事件与状态更新时序发生变化
→ 延迟同步逻辑未及时写入用户最后输入值
→ 页面展示值、表单状态、请求参数或落库值出现偏差
→ 用户无法及时发现或系统未阻止异常提交
→ 异常订单继续产生
→ 业务侧先反馈个别现象，但未立即按高风险事故升级
→ 后端通过全量数据排查发现大范围异常
→ 研发复现并定位 RN 版本兼容问题
→ 热更新修复上线
```

## 五、原因分析

### 5.1 直接原因

部分操作场景下，用户最后填写的价格没有被正确同步到提交数据，提交时读取了旧值或默认值，造成用户看到的值与实际订单数据不一致。

### 5.2 技术原因

1. 终端订单上报页面支持多产品录入，原逻辑为避免每次输入都触发表单状态更新和页面重渲染，采用输入结束后再同步表单数据的处理方式。
2. 该处理方式依赖原有输入事件和状态更新顺序。
3. RN 0.86 升级后，事件触发或状态更新时序出现变化，原逻辑在部分场景下失效。
4. 提交时没有再次从可靠的数据源读取并校验用户最终输入值。
5. 关键数据写入链路没有形成页面展示值、请求参数和服务端落库值的一致性防线。

### 5.3 流程原因

1. RN 框架升级前没有覆盖多产品录入、高频输入、快速提交、多机型和弱网等高风险场景。
2. 针对性能优化而引入的特殊输入同步逻辑，没有进行专项兼容性评估。
3. 缺少版本升级后的灰度观察和业务数据核对。
4. 缺少异常数据监控，无法主动发现生产范围内是否持续产生异常。
5. 缺少关键数据写入的后端拦截、告警或异常隔离机制。

### 5.4 事故响应与组织原因

1. 最初只有一两名业务员反馈设备或页面出现 0 值，团队没有将其识别为可能影响数据完整性的高风险信号。
2. 事故响应主要依赖业务侧继续反馈，没有及时主动查询所有生产用户和全量数据。
3. 在影响范围尚未确认时，没有及时采取关闭、回退、降级或后端拦截等紧急止损措施。
4. 后端在排查是否可以通过同区域数据对比恢复时，才发现存在几千条异常订单，说明前后端缺少共同的影响评估和数据核查流程。
5. 业务线负责人当时忙于其他事项，没有及时接管或明确安排副手接管。
6. 问题模块成员主要埋头排查技术问题，没有主动寻求团队帮助、同步不确定性或提出止损建议。
7. 团队缺少通用线上事故流程、事故负责人接管规则和跨团队协作机制。

## 八、需要沉淀的团队判断

1. 线上异常不能按反馈人数判断严重程度。涉及核心数据写入时，一个用户反馈也可能是大范围事故的早期信号。
2. “业务允许填写某个值”不等于“系统产生该值就是正常”。需要结合用户操作、版本、历史基线和上下游数据判断。
3. 技术问题解决前，优先判断异常是否仍在扩大；技术恢复稳定后，再评估数据恢复和业务补救。
4. 事故负责人负责组织，不要求亲自定位；技术处理负责人负责解决，不应独自承担跨团队协调。
5. 业务线负责人忙于更高优先级事项时，必须明确授权副手接管，不能让事故停留在模块成员手中。
6. 角色负责人应持续知情，但不默认成为共同指挥者；跨业务线、重大风险或无法推进时再升级或接管。
7. APP 的质量要求不仅是功能能用，还要保证输入、状态、请求、服务端结果和用户感知之间的可靠一致性。
